# แผนยุทธศาสตร์การขยายระบบและลดภาระฐานข้อมูล (Scalability & Load Isolation Roadmap)

**วันที่บันทึก:** 2026-11-18  
**สถานะ:** Draft / Parked (บันทึกไว้สำหรับดำเนินการในเฟสถัดไป)  
**บริบท:** เตรียมความพร้อมระบบ Lao_Lotto รองรับจำนวนเจ้ามือ (Dealer) และสมาชิกจำนวนมาก โดยเฉพาะช่วงเวลาโหลดสูงสุดพร้อมกัน (Peak Concurrency)

---

## 1. บริบทและปัญหาที่คาดว่าจะเกิดขึ้น (Problem Statement)

ระบบหวยมีลักษณะทราฟฟิกแบบ **"Thundering Herd" (โหลดพุ่งสูงพร้อมกันในช่วงเวลาสั้นมาก)** แบ่งเป็น 2 ช่วงวิกฤตที่เกิดขึ้นพร้อมกันทุก Dealer:
1. **ช่วงก่อนปิดรับแทง (15–30 นาทีสุดท้าย):** สมาชิกส่งโพยผ่าน LINE Bot และเว็บพร้อมกัน (`INSERT submissions`) ขณะเดียวกันเจ้ามือทุกเจ้ารีเฟรชดูยอดรวมเลข ยอดเกิน และทำรายการตีออก (`bet_transfers`) ถี่มาก
2. **ช่วงหลังประกาศผล (1–10 นาทีแรก):** ระบบประมวลผลรางวัลและอัปเดตโพยถูก พร้อมกับสมาชิกทุกคนรุมสั่ง `/สรุป`, `/โพยถูก` และเปิดดูประวัติพร้อมกัน

---

## 2. สรุปผลการวิเคราะห์แนวคิด "แยก DB ลงเครื่อง Local ของแต่ละ Dealer"

> **ข้อสรุป:** แนวคิดเรื่อง **การแยกโหลดรายเจ้ามือ (Tenant Isolation)** ถูกต้องมากในเชิงสถาปัตยกรรม แต่ **ไม่แนะนำให้นำเครื่อง Local ของเจ้ามือมาเป็น Primary Database หลัก**

### ความเสี่ยงหลักหากใช้เครื่อง Local เป็น Primary DB
1. **LINE Bot ดับเมื่อเครื่องเจ้ามือมีปัญหา:** LINE Webhook ต้องการ Public HTTPS ที่เสถียร 24 ชม. และตอบเร็ว (< 1–2 วินาที) หากเครื่องเจ้ามือปิด, เน็ตบ้านหลุด, ไฟดับ หรือ IP เปลี่ยน → บอทดับทั้งกลุ่มทันที
2. **Multi-Device & ทีมงาน:** เจ้ามือ/แอดมิน/ผู้จัดการกลุ่มใช้งานพร้อมกันหลายอุปกรณ์ และสมาชิกต้องเปิดเว็บ/ดูสรุปจากมือถือได้ทุกที่ทุกเวลา
3. **ฟีเจอร์ตีออกเชื่อมโยงในระบบ (`is_linked = true`):** เจ้ามือ A ตีออกตรงเข้าสู่งวดของเจ้ามือ B (`target_round_id`, `target_submission_id`) หากข้อมูลอยู่คนละเครื่อง Local การควบคุมความถูกต้องของ Transaction ข้ามเครื่องทำได้ยากและเสี่ยงยอดไม่ตรง
4. **ความปลอดภัยและความน่าเชื่อถือ (Data Integrity & Billing):** เสี่ยงฮาร์ดดิสก์พัง/ไวรัส/ข้อมูลหาย และเปิดช่องให้แก้ตัวเลขในเครื่อง Local เองได้ ทำให้ SuperAdmin ตรวจสอบยอดเครดิตและส่วนแบ่งกำไรได้ยาก
5. **ภาระการอัปเดต Schema (Migration):** ปัจจุบันระบบมี Migration กว่า 260+ ไฟล์ การอัปเดตฐานข้อมูลบนเครื่องลูกค้าจำนวนมากพร้อมกันเสี่ยง Schema พังและดูแลยากมาก

## 3. คอขวดที่แท้จริงของระบบในปัจจุบัน (Current Bottlenecks)

PostgreSQL ใช้กลไก **MVCC (Row-Level Lock)** ทำให้การบันทึกข้อมูลของเจ้ามือ A **ไม่ได้เกิด Table Lock ข้ามเจ้ามือ** ไปขวางเจ้ามือ B ปัญหาความหน่วง/ชนเพดานจริงๆ มาจาก 3 ปัจจัยหลัก:

1. **การดึง Raw Rows มาคำนวณฝั่ง JS (`fetchAllRows` & LINE Bot):**
   - หน้า `src/components/dealer/RoundAccordionItem.jsx` และ `supabase/functions/line-bot/index.ts` ดึงข้อมูลดิบจาก `submissions` แบบวน Pagination ทีละ 1,000 แถว มาบวกรวมในหน่วยความจำ JavaScript ทุกครั้งที่เปิดดูหรือสั่ง `/สรุป`
   - หากงวดหนึ่งมี 5,000 แถว และมีคนเรียกดูพร้อมกัน 100 คน = ฐานข้อมูลต้องส่งข้อมูลถึง 500,000 แถวในไม่กี่วินาที
2. **การคำนวณซ้ำหลังประกาศผล:**
   - เมื่อประกาศผลแล้ว คำสั่ง `/สรุป` และ `/โพยถูก` ยังมีการสแกนและคำนวณจาก `submissions` ดิบซ้ำๆ แทนที่จะอ่านจากตารางสรุปที่คำนวณเสร็จแล้ว
3. **ข้อจำกัดของ Supabase Tier และการโตของตารางสะสม:**
   - ข้อจำกัด Free Tier (500MB, 1,000 rows/req, CPU แชร์, Connection จำกัด) และตาราง `submissions` ที่เก็บสะสมทุกงวดโดยยังไม่ได้แยก Archive (Hot/Cold Data)

## 4. แผนยุทธศาสตร์การขยายระบบ 3 เฟส (Phased Roadmap)

### เฟส 1: Quick Wins — ลดภาระ DB ลง 80–90% บนฐานข้อมูลเดียว (รองรับ 10 – 100 เจ้ามือ)
*เป้าหมาย: ได้ความลื่นแบบ Local บนเครื่องเจ้ามือ โดยยังคงความเสถียรและปลอดภัยของ Cloud DB*

- [ ] **1.1 Hybrid Local-First ใน Browser ของเจ้ามือ (Incremental Sync + Local Cache)**
  - โหลดโพยของงวดที่กำลังเปิดมาเก็บใน Browser Memory / IndexedDB เพียงครั้งเดียว
  - หลังจากนั้นดึงเฉพาะข้อมูลส่วนต่าง (Delta Sync: `WHERE updated_at > last_synced_at` หรือ Realtime Insert) แทนการรีโหลดใหม่ทั้งงวด
  - งานคำนวณหนักๆ (รวมยอดเลข, เช็กยอดเกิน, กราฟตีออก, จำลองสถานการณ์ผ่าน Web Worker อย่าง `scenarioWorker`) ให้ประมวลผลบนเครื่องเจ้ามือ 100% และยิงกลับ DB กลางเฉพาะตอนกด **"ยืนยันตีออก"**
- [ ] **1.2 ย้ายการรวมยอด (Aggregation) ไปทำเป็น PostgreSQL RPC**
  - สร้าง SQL RPC ใช้ `GROUP BY bet_type, numbers` สำหรับหน้าดูยอดรวม/ยอดเหลือ/ยอดเกิน ให้ส่งกลับเฉพาะแถวสรุป (ลดปริมาณข้อมูลผ่าน Network ลง 10–20 เท่า)
- [ ] **1.3 Pre-computed Summary หลังประกาศผล (แก้คอขวด `/สรุป` และ `/โพยถูก`)**
  - เมื่อประกาศผล ให้ประมวลผลลงตารางสรุป (`user_round_history`, `round_history`, `upstream_round_summary`) **ครั้งเดียวจบ**
  - ปรับ LINE Bot `/สรุป` และหน้าประวัติให้ Query อ่านจากตารางสรุปเพียง **1 แถวต่อสมาชิก (Index Lookup)** แทนการสแกน `submissions` ทั้งงวด
- [ ] **1.4 Composite Indexing & Hot/Cold Data Archiving**
  - ตรวจสอบและเพิ่ม Composite Index ให้ตรงกับ Query หลัก เช่น `(round_id, user_id, is_deleted)`, `(round_id, is_winner)`
  - ทำ Automated Job (via `pg_cron`) ย้าย `submissions` ของงวดที่ปิดและเคลียร์ยอดแล้วเกิน 3–6 เดือนไปไว้ที่ `submissions_archive` เพื่อให้ตาราง Active เล็กและเร็วตลอดเวลา
- [ ] **1.5 อัปเกรด Infrastructure เมื่อรายได้และโหลดถึงจุดคุ้มทุน**
  - อัปเกรด Supabase เป็น **Pro Tier** + เปิดใช้งาน **Supavisor Connection Pooler (Transaction Mode)** สำหรับ Edge Functions เพื่อลดปัญหา Connection เต็มช่วงใกล้หวยออก

---

### เฟส 2: แยกท่ออ่าน/เขียน และ Caching Layer (รองรับ 100 – 500+ เจ้ามือ)
*เป้าหมาย: ป้องกันไม่ให้งานอ่านรายงาน/สรุปยอดไปแย่ง Resource ของการรับแทง*

- [ ] **2.1 Read Replica (แยก DB เขียน กับ DB อ่าน)**
  - **Primary DB:** รับเฉพาะงานเขียนสำคัญ (LINE Bot รับโพย, บันทึกตีออก, ประกาศผล, อัปเดตยอดจ่าย)
  - **Read Replica:** รับงานอ่านหนักทั้งหมด (หน้ารายงานเจ้ามือ, ประวัติย้อนหลัง, `/สรุป`, `/โพยถูก`, SuperAdmin Dashboard)
- [ ] **2.2 Distributed Cache (Upstash Redis)**
  - แคชข้อมูลที่ถูกอ่านซ้ำถี่มาก เช่น `lottery_rounds` ที่กำลังเปิด, `user_settings`, `number_limits` และผลสรุปงวดที่ประกาศผลแล้ว (TTL 30–60 วินาที หรือ Invalidate เมื่อมีการแก้ไข)
- [ ] **2.3 Async Background Queue สำหรับการประกาศผล**
  - แยกงานคำนวณผลรางวัลและการส่ง Flex Message แจ้งเตือนเข้าคิวประมวลผลทีละ Batch/ทีละ Dealer เพื่อไม่ให้เกิด CPU Spike พร้อมกันในวินาทีเดียว

---

### เฟส 3: Cloud Sharding / Cell-Based Architecture (รองรับ 500 – 5,000+ เจ้ามือ)
*เป้าหมาย: นำแนวคิด "แยก DB ต่อเจ้ามือ" มาใช้งานจริงบน Cloud แบบ Enterprise*

- [ ] **3.1 Central Control Plane (DB กลางสำหรับ SuperAdmin)**
  - เก็บเฉพาะบัญชีผู้ใช้, ตาราง Routing (`dealer_id` → `shard_id`), ระบบเครดิต/Billing และยอดสรุปรายงวด (Sync มาเฉพาะตัวเลขสรุป ไม่เก็บโพยดิบ)
- [ ] **3.2 Data Plane แยกตามระดับลูกค้า (Cloud Shards)**
  - **Standard Tier (Shared Shards):** แบ่งเจ้ามือ 30–50 รายต่อ Cloud DB 1 ก้อน (Shard 1, Shard 2, ...) ขยายเพิ่ม Shard ใหม่ได้ไม่จำกัด
  - **VIP Tier (Dedicated Cloud DB):** แยก Cloud DB ส่วนตัว 1 ก้อนต่อ 1 เจ้ามือ ได้ Isolation 100% โดยยังออนไลน์ 24 ชม., มี Auto-Backup, รองรับ LINE Bot และรัน Migration อัตโนมัติพร้อมกันทุก Shard ผ่าน CI/CD
- [ ] **3.3 Cross-Shard Linked Transfers Protocol**
  - ออกแบบ API/Event Relay สำหรับกรณีเจ้ามือต่าง Shard ตีออกเชื่อมโยงกัน (`is_linked = true`) ให้รองรับ Idempotency Key และ Retry เพื่อป้องกันโพยตกหล่นหรือซ้ำซ้อน

## 5. เกณฑ์ตัดสินใจขยับเฟส (Scaling Triggers)

| สัญญาณที่พบจริงในระบบ | การดำเนินการที่แนะนำ |
| :--- | :--- |
| งวดหนึ่งเริ่มมีรายการเกิน 2,000–5,000 แถว หรือหน้าจอเจ้ามือโหลดช้าตอนใกล้หวยออก | เริ่ม **เฟส 1.1 – 1.3** (Incremental Sync + SQL RPC + Pre-computed Summary) |
| พื้นที่ DB แตะ 350MB+ หรือเจอ Connection / CPU เต็มช่วง 15:00–15:30 | เริ่ม **เฟส 1.4 – 1.5** (Archiving + อัปเกรด Supabase Pro + Pooler) |
| เจ้ามือใช้งานพร้อมกัน > 80–100 ราย และงานอ่านรายงานเริ่มดึงให้ LINE Bot ตอบช้า | เริ่ม **เฟส 2** (Read Replica + Redis Cache + Queue) |
| เจ้ามือ > 300–500 ราย หรือมีลูกค้ารายใหญ่ (VIP) ต้องการแพ็กเกจแยกเซิร์ฟเวอร์เฉพาะ | เริ่ม **เฟส 3** (Control Plane + Cloud Shards / Dedicated DB) |
